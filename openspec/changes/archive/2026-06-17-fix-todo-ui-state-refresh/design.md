## Context

TODO 工作区当前把业务状态同步和 TODO 工程 UI 状态恢复耦合在同一条前端路径里。`applyState()` 每次接收后端 ProjectState 都会重新应用当前 TODO 工程的 UI 状态，包括 TODO 视图标签和左侧 TODO 栏宽度。

这在打开 workspace 或用户主动选择 TODO 工程时是正确行为，但在创建 TODO、更新 TODO、开始 TODO、完成 TODO、删除 TODO、终端状态刷新等普通业务刷新中会覆盖用户当前界面。典型结果是：用户调整过的侧栏宽度回到已保存宽度或默认宽度；点击开始后本地先切到 `执行中`，随后被普通状态刷新恢复到旧视图。

## Goals / Non-Goals

**Goals:**

- 将 TODO 工程 UI 状态恢复限制在打开 workspace、前端重新加载和用户主动选择 TODO 工程等显式恢复场景。
- 让普通 ProjectState 刷新保持当前左侧 TODO 栏宽度和当前 TODO 视图。
- 保证用户点击开始 TODO 后界面停留在 `执行中` 视图并显示该 TODO。
- 保留现有按 TODO 工程保存视图标签和侧栏宽度的能力。

**Non-Goals:**

- 不修改后端 ProjectState 数据结构。
- 不迁移或改写已有 TODO 工程 UI 状态持久化文件。
- 不改变 TODO 工作流状态的合法转换规则。
- 不改变侧栏宽度的最小值、最大值或终端 fit 机制。

## Decisions

### 区分业务状态应用和 UI 状态恢复

`applyState()` 应支持调用方表达是否恢复 TODO 工程 UI 状态。默认业务刷新不恢复 UI 状态；打开 workspace、加载 TODO 工程 UI 状态完成后、用户主动选择 TODO 工程时才恢复。

这样可以保持大多数现有状态同步逻辑不变，只把 `applyTodoProjectUIState()` 从无条件调用改为显式调用，避免普通刷新覆盖用户当前界面。

备选方案是每个会触发业务刷新的 action 单独保存和恢复宽度、视图。这个方案分散且容易漏掉新增 action，因此不采用。

### 保留用户操作的即时视图切换

开始 TODO 的交互已经在侧栏组件中把当前视图切换到目标状态。父组件收到 `change-todo-status` 后不应在后端返回时用旧持久化视图覆盖该即时切换。

如果实现中发现本地即时切换只在有 active TODO 工程时才持久化，需要确保无 active TODO 工程或当前 TODO 工程缺失 UI 状态时也不会被 `applyState()` 重置回 `未执行`。

### 持久化仍由用户调整触发

TODO 视图标签仍在用户点击标签时保存，侧栏宽度仍在拖动结束时保存。普通业务刷新不应自动保存当前 UI 状态，也不应从持久化文件重新读取覆盖当前状态。

## Risks / Trade-offs

- 普通刷新不恢复 UI 状态后，某些路径如果实际代表“切换到另一个 TODO 工程”但没有显式标记恢复，可能继续显示上一个 TODO 工程的 UI 偏好。缓解方式是在选择 TODO 工程和打开 workspace 的路径上明确传入恢复选项，并用测试覆盖。
- 当前 `applyState()` 调用点较多，遗漏调用语义可能造成行为不一致。缓解方式是让默认行为保护用户当前 UI，仅在少数显式恢复场景 opt-in。
- UI 状态恢复与终端 fit 有依赖。缓解方式是保留宽度变化和显式恢复后的 `scheduleFitActiveTerminal()`，普通业务刷新不额外触发宽度变化。
