## Context

当前项目侧栏由 `ProjectSidebar.vue` 渲染，项目列表 `.project-list` 是纵向滚动容器。终端启动菜单挂在项目行内的 `.terminal-launch-control` 下，并通过绝对定位向下展开。由于滚动容器会裁剪纵向溢出，列表底部项目打开菜单时，菜单下半部分可能不可见。

这个变更只处理项目树内终端启动菜单的可见性，不改变终端创建、启动 profile 配置或后端状态模型。

## Goals / Non-Goals

**Goals:**

- 用户在项目列表底部项目点击加号时，终端启动菜单仍保持可见并可操作。
- 菜单内容、选项顺序、点击选择、外部点击关闭等现有行为保持不变。
- 保持项目列表本身可滚动，长项目列表仍能正常浏览。
- 通过测试覆盖底部边界场景，防止回归。

**Non-Goals:**

- 不重构整个弹层系统，不引入新的菜单/浮层依赖。
- 不改变启动 profile 的配置、保存或校验逻辑。
- 不改变项目树的数据结构或后端 API。

## Decisions

1. 使用项目列表可视区域感知的菜单定位。

   打开菜单时读取触发按钮和 `.project-list` 的可视边界，计算菜单向下展开是否有足够空间。如果下方空间不足且上方空间更合适，则将当前菜单标记为向上展开。

   备选方案是给 `.project-list` 增加固定 `padding-bottom`。该方案实现最小，但会让列表底部长期出现空白，并且无法适配启动 profile 数量变化。

2. 在可用空间极小时约束菜单高度并允许菜单内部滚动。

   当窗口高度较小或启动 profile 数量很多时，向上或向下都可能无法完整容纳菜单。此时菜单容器应限制在项目列表可视范围内，内部选项仍可滚动访问，避免被外层项目列表裁剪。

   备选方案是把菜单 Teleport 到 `body`。这可以完全绕过滚动容器裁剪，但会引入更多定位、主题、关闭逻辑和层级管理复杂度。当前只有一个小菜单存在该问题，局部定位更合适。

3. 只保留一个打开菜单的状态，并保存该菜单的展示方向/最大高度。

   现有组件已经使用 `openLaunchProjectId` 保证同一时间只打开一个菜单。实现时可以在该状态旁维护当前菜单 placement 和可选的高度约束，避免为每个项目维护一组 DOM 测量状态。

## Risks / Trade-offs

- [DOM 测量在 jsdom 中不可靠] → 单元测试应直接验证状态/class/样式约束的计算入口，必要时 mock `getBoundingClientRect`，不要依赖真实浏览器布局。
- [菜单打开后 profile 数量或窗口高度变化] → 打开菜单时计算一次即可覆盖当前问题；后续如需要可在 resize 或 profile 变化时复算，但本变更不扩大到全局浮层系统。
- [菜单内部滚动增加一个滚动区域] → 只在空间不足时启用高度约束，常规高度下仍显示完整菜单。
